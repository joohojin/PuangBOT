### 🤔 생각 및 분석 내용
- 사용자가 첨부한 디스코드 로그를 확인한 결과, `ffmpeg process XXXX has not terminated. Waiting to terminate...`라는 경고가 주기적으로 반복해서 뜨고 있었습니다.
- 이 로그는 `discord.py` 내부에서 `ffmpeg` 프로세스를 강제로 종료(`kill()`)할 때 발생하는 정상적인 알림입니다. 하지만 이것이 매번 1초 만에 즉각적으로 뜨는 것은 비정상입니다.
- **최초의 TTS는 성공적으로 종료되었으나(return code 0), 그 이후의 모든 TTS는 시작하자마자 즉시 강제 종료되었습니다.**
- 분석 결과, 다음과 같은 두 가지 겹치는 버그가 존재했습니다.
  1. **오래된 참조 버그 (Stale Reference Bug):** `process_tts_queue` 내부에서 사용하는 `guild.voice_client`와 `start_mixer_if_needed`에서 사용하는 `state.voice_client`가 동기화되지 않는 문제가 있었습니다. 봇이 내부적으로 채널에 재연결되거나 처음 연결될 때 `state.voice_client`가 업데이트되지 않으면, 봇은 연결이 끊겼다고 오판하여 즉시 TTS 소스를 폐기(`cleanup`)해 버렸습니다.
  2. **오디오 믹서 경쟁 상태 (Mixer Race Condition):** TTS 재생 후 이전 오디오 스레드가 종료 중일 때(`voice.is_playing() == True`이나 스레드는 종료 루틴 실행 중), 새로운 TTS가 들어오면 `start_mixer_if_needed`가 재생 중으로 착각하고 새 믹서를 시작하지 않았습니다. 그리고 기존 스레드는 종료되면서 큐에 막 들어온 새 TTS를 파기해버렸습니다.

### 🏗️ 설계 및 계획
- `process_tts_queue` 함수가 반복문을 돌 때마다 `guild.voice_client`의 최신 상태를 확인하고 `state.voice_client`를 지속적으로 최신화하도록 수정합니다.
- `start_mixer_if_needed` 함수에서 `state.voice_client`가 유효하지 않은 경우, `bot.get_guild(guild_id).voice_client`를 통해 한 번 더 최신 보이스 클라이언트를 가져와서 덮어씌웁니다.
- `voice.is_playing()`이 `True`이더라도, `state.mixer`가 `None`인 상태(오래된 플레이어 스레드가 죽어가는 중)라면 낡은 플레이어를 강제로 멈추고(`voice.stop()`) 새로운 믹서가 정상적으로 재생을 시작하도록 예외 처리를 추가합니다.
